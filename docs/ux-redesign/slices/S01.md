# S01 — UX specification and low-fidelity wireframes

**Status:** Complete for design planning; not runtime implementation
**Purpose:** Define observable student journeys and interaction requirements before workspace implementation.
**Scope:** UX flows, information architecture, screen states, responsive behavior, accessibility, and low-fidelity wireframes. No production code, database, or API contract changes.

## Required reading and source of truth

1. Read [the current-state audit](../research/current-state-audit.md) and inspect its linked evidence before making claims about existing behavior.
2. Use [the UX specification](../research/ux-spec.md) as the finalized S01 design baseline. It incorporates the user-supplied `ux-spec.md`; preserve its product principles, five screens, journeys, state matrix, responsive behavior, component hierarchy, navigation, resolved decisions, and explicit future-feature labels.
3. The audit wins over assumptions in the proposal about what is currently implemented. In particular, S00 remains partial; the eraser event trace, physical stylus behavior, and PostgreSQL E2E remain unresolved.
4. Treat competitor products as inspiration only. Do not copy distinctive assets or claim competitor research without citations and actual validation.

## Work instructions

- Finalize Home, Library, Mathematics Workspace, AI Review, and Trash wireframes for tablet and phone. Specify behavior at compact widths, split-screen, rotation, fold, and keyboard/IME appearance.
- Validate the specification against all eight journeys J01–J08; report design coverage separately from runtime implementation.
- For every action, distinguish current behavior from a design proposal and a future/deferred capability. Do not present placeholder Add Page, zoom, undo, math review, cloud, or trash actions as working features.
- Specify entry, primary action, alternatives, error/recovery, exit, and visible status for each major journey.
- Record accessibility semantics, focus return, 48 dp touch-target target, system-bar/cutout insets, TalkBack order, and touch-versus-stylus policy.
- Preserve the confirmed S00 risks in the spec. Route remedies to later implementation slices; do not fix them in this design slice.
- Preserve resolved UX decisions as design constraints; S02 owns storage, page identity, revision and API choices.

## Acceptance criteria

- [x] Annotated tablet and phone low-fidelity layouts cover Home, Library, Mathematics Workspace, AI Review, and Trash.
- [x] J01–J08 specify happy path, alternate path, error/recovery, exit, and feedback; the validation matrix distinguishes design coverage from runtime status.
- [x] Responsive behavior preserves document, selected tool, active page, and viewport across layout changes.
- [x] UI state matrix covers empty, loading, success, error/offline, and recovery where applicable.
- [x] Accessibility, navigation/focus behavior, status language, and six walkthrough requirements are recorded with measurable targets.
- [x] Continuous-page behavior, collapsible-panel coexistence, toolbar scope, and feedback progression are resolved for planning with technical gates.
- [x] S02 data, revision, migration, transform, analysis, conflict, compatibility, and authorization dependencies are documented in the UX spec.
- [x] `PROGRESS.md` is updated. The user explicitly requested finalization; user testing and runtime validation remain future evidence, not prerequisites to completing this design baseline.
