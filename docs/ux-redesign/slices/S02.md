## Decision tracks

Create one architecture decision record (ADR) per track. Each ADR must state context and verified current behavior, decision status, options considered, recommendation/decision and rationale, consequences, open questions, implementation gates, and measurable acceptance criteria. A recommendation is not an approved product or security decision unless explicitly marked approved.

### S02-A — Document, Page, and WorkSession identity and ownership

- Define stable identity and lifecycle for Document, Page, and WorkSession, and their cardinality/ownership relationships.
- Decide what the existing `workSessionId` identifies, how it relates to a durable document, and how pages/strokes are scoped.
- Include create, rename, reorder, delete/restore, clear, and document deletion lifecycle semantics; distinguish proposed features from current runtime support.
- Deliver a domain model and UML-style relationship/lifecycle diagram, plus invariants and identity examples.

### S02-B — Durable local storage and pending-event outbox

- Compare viable Android local persistence options against current dependencies, ink serialization needs, transaction guarantees, lifecycle/process-death behavior, and testability.
- Define the local source of truth, canonical serialized stroke representation, atomic persistence of state plus pending operations, outbox delivery/acknowledgment, and crash behavior.
- Explain how current in-memory `StudentWork` and pending changes migrate without losing or replaying edits; identify backup/restore and corruption recovery behavior.
- Deliver a persistence/data-flow diagram, transaction and failure matrix, serialization/versioning proposal, migration plan, and measurable recovery/sync acceptance criteria.

### S02-C — Page operations, revisions, and API compatibility

Depends on S02-A and S02-B. Define page-scoped operations and ordering, document-wide versus page-scoped revision semantics, idempotency, transactional acknowledgment, version negotiation, and unsupported-client behavior. Include concrete request/response examples and migration/backward-compatibility strategy.

### S02-D — Canvas coordinates and geometry

Define canonical page-local units and dimensions, viewport state, rendering/input transforms and inverse, zoom/pan, hit testing, eraser accuracy, and property-based or invariant tests. Stored strokes must not change when viewport transforms change.

### S02-E — Android Compose/MVVM and adaptive shell

Define navigation ownership, screen state versus durable document/session state, repository boundaries, lifecycle survival, panel/layout state, and adaptive-layout responsibilities. Preserve the S01 requirement that layout changes do not reset document, tool, or viewport state.

### S02-F — Synchronization and AI-analysis lifecycles

Separate durable local commit, upload/outbox, server acknowledgment, analysis request, revision-bound result, stale/cancel/retry, and unavailable/uncertain states. Specify ownership and contracts without presenting the current ink synchronization endpoint as mathematical analysis.

### S02-G — Recovery, authorization, migration, and validation strategy

Define non-destructive conflict and recovery behavior, authorization and ownership requirements, data/schema/event migration ordering, compatibility gates, security review boundaries, and end-to-end validation strategy. A UUID or possession of a `workSessionId` is not authorization.
